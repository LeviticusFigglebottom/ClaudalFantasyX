## Goal
In the Lead's batch-5 gate (lead/batch5), the capture process for `shrine_s01_approach` hung: 18+ minutes at about 4% CPU after `ShellShrineLevel: GI baked (2 states) in 4571 ms`, until the Lead killed it. `shrine_s02_threshold` then hung the same way (13+ minutes after `GI baked ... in 4216 ms`). In the symbol-less backtrace, the main thread sits in `pthread_cond_wait` and all four WorkerThreads in `pthread_mutex_lock`. Find the lock cycle, fix it if it is ours, and stop a hung shot from stalling a gate for an hour.

## Acceptance criteria
- [x] Reproduce it: loop the shot and the shrine_* block on lavapipe (niced, LP_NUM_THREADS=4, about 15 runs, a per-run timeout this task starts and kills), and record the rate. *(0 hangs in 62 processes; see Notes.)*
- [x] Every thread's stack with symbols, and the lock cycle named. *(The Lead's own hung process, symbolised offline. No new hang was caught live.)*
- [x] Fix it in our code, or document the engine bug the way M1-QA-10 did and give the narrowest project-side mitigation. Don't suppress symptoms. *(An engine bug. The mitigation is `warm_shader_groups` on the shrine shots.)*
- [x] capture.sh: a per-shot hang guard that kills only that shot's processes, names it in `CAPTURE PROCESS EXIT`, and fails the gate.
- [x] No baseline changes.

## Notes (qa, agent-a37fd6e168e22842f, 2026-10-24; reviewer: lead)
- **Root cause: a Godot 4.6.3 engine deadlock in `ShaderRD`. It is not our code, and the bake is not in it.** `ShaderRD::version_get_shader()` (shader_rd.h:179-209) takes the shader version's `mutex`. If one of the version's compile groups is still pending, it calls `_compile_version_end()`, and that calls `WorkerThreadPool::wait_for_group_task_completion()` *while still holding the mutex*. That wait is a plain semaphore wait: the waiting thread runs no tasks, and the version mutex is not one of the pool's "unlockable" locks. Pipeline compiles run as pool tasks (`ShaderData::_create_pipeline`), and they reach the same `version_get_shader()` and the same mutex through `_get_shader_variant()`. The pool's queue is FIFO (`task_queue.add_last` for high priority too). So when every worker has picked a pipeline compile for that shader *before* the shader's own group tasks, every worker blocks on the mutex. The group's tasks never start, and the main thread never wakes up. Godot master still has the same `version_get_shader()`.
- **The Lead's hung process, symbolised.** I found its load base (0x7f38c5e00000) by matching the return addresses against `pthread_mutex_lock@plt` call sites, then resolved the frames against the pinned build's debuginfod symbols. Thread 1 (main): `WorkerThreadPool::wait_for_group_task_completion` <- `ShaderRD::_compile_version_end` <- `SceneShaderForwardClustered::ShaderData::_get_shader_variant`. WorkerThreads 0-3: `pthread_mutex_lock` (<mutex>:130) <- `_get_shader_variant` <- `ShaderData::_create_pipeline`. The llvmpipe threads were idle, and the audio driver thread (`OS_Unix::delay_usec`) was idle. No audio, stream-load or bake frame is anywhere in the process. The resolved list is `docs/kb/qa/shrine_hang_bt_symbolised.txt`.
- **Why the shrine, and why lavapipe.** Forward+ compiles its "advanced" scene-shader group (VoxelGI, motion vectors, SSS, lightmap variants) lazily. The first frame that needs it calls `ShaderRD::enable_group()`, which queues that group's compile for *every shader already loaded*, behind all the pipeline compiles already queued. The shrine shots are the only shots with TAA off and a VoxelGI. Every TAA shot turns the group on during frame 1, when it has loaded little. The shrine turns it on during its first frame after the bake, with the whole hall loaded. A gdb trace (`ShaderRD::enable_group` and `_compile_version_end`, non-stopping, cold `user://`) shows `enable_group(ADVANCED)` firing 7 s after `GI baked`. After it, the main thread waits on the late groups for up to 8.5 s at a time while holding each shader's mutex, about 13 s in all. On a GPU the compiles take milliseconds, so the window is tiny (the PC: 20/20 clean). On lavapipe it takes seconds.
- **Repro rate: 0 hangs in 57 lavapipe processes**, with LP_NUM_THREADS=4, niced, and load 2 to 9.5 (another gate was running). Before the fix there were 29: s01 alone 12 times (1 with a fresh `user://`, 10 cold, 1 under the gdb trace), the shrine block in manifest order twice (10 processes, from a copy of the Lead's gate `user://`), and s01 7 times with the pool capped at 2 workers (a temporary `override.cfg`, since removed; 1 of the 7 under the queue-walk trace). After the fix there were 28: s01 cold 12 times plus once under the trace, and the block through `capture.sh` 3 times (15 processes) with compare. A queue walk at each main-thread group wait (gdb Python, `WorkerThreadPool::task_queue`) found up to 28 pipeline compiles queued ahead, but none for the shader being waited on. So the cycle needs a timing the Lead's machine hit twice and this one never did. "Flake" is not the finding: the cycle is proven from the Lead's process and from the engine source.
- **Not audio** (the Lead's suspicion). The hung process has no audio frame. Every run here was on batch 5, which includes claude/audio, and none hung. m2-slice's clean full gate and the PC's 20/20 fit the same picture: both rest on the timing, not on a missing commit.
- **Mitigation (capture, narrow): `"warm_shader_groups": true` on the five shrine shots.** Before the shot's scene loads a single shader, `capture.gd` renders an empty 8 px world through a TAA SubViewport, using `RenderingServer.force_draw(false, 0.0)` (frame_step 0, so TIME does not move). That turns the advanced group on while only the engine's own shaders exist. Every shrine shader then queues all its groups when it is created, ahead of any of its own pipeline compiles, so the main thread never waits on a late group that its pipelines can starve. The trace confirms it: `enable_group(ADVANCED)` now fires before the level loads, and capture time is 44 s instead of 67 s. The key adds one to the frame count, so it is only for non-TAA shots (TAA jitter follows the frame count). That covers any future non-TAA shot with VoxelGI, SSS or a lightmap. **Pixels:** the baselines are unchanged and still pass. Before the fix, every shrine capture here matched them at RMSE 0.00000. After it, all 4 post-fix runs give the same deterministic values: s01 0.00014, s02 0.00022, s03 0.00034, s04 0.00042, s05 0.00000 (limit 0.008). That is the one-frame shift of some frame-indexed effect (temporal noise or jitter), not a visual change. If the Lead wants exact matches again, re-approve those five baselines. The bake is unchanged (the Lead: the bake's frame cost belongs to m2-slice).
- **Game side (not fixed here):** a player with TAA off who reaches a VoxelGI room as the first scene that needs the advanced group has the same, mostly theoretical, exposure on slow CPUs. Requested as M2-RND-14 (rendering): turn the group on at boot whatever the AA setting, in the prewarm bring-up. The engine fix itself (releasing the version mutex around the group wait, or waiting collaboratively) goes into the M1-ARC-17 / ADR 0032 engine-build decision. It is listed in the "Engine deadlock" section of `docs/kb/qa/screenshots.md`.
- **capture.sh hang guard:** each shot process runs under `timeout -k 30 $HYMN_SHOT_TIMEOUT` (default 600 s; in shared mode the limit is multiplied by the shot count). timeout(1) signals only its own process group, which holds Godot and the wrapper's Xvfb. A hung shot is logged as `CAPTURE PROCESS EXIT 124 (hung: killed after 600 s): <id>`, the shots after it still run, and capture.sh exits 124, so the gate fails. `tools/tests/test_capture_hang_guard.py` covers it (the kill, the children, the name, the shared-mode limit, a clean run). It builds on M2-NIT-04's capture.sh (lead/batch4, a91a6774): its capture.sh and `test_capture_sh.py` are taken as is, so the merge is the same text.
- **Gate:** see the handoff `docs/kb/handoffs/2026-10-24-qa-2.md`.
